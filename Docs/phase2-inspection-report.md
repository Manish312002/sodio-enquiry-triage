## 7. Malformed / ambiguous boundaries — **REPORT REQUIRED**

### 7a. Form-feed (`\x0c`) characters from `pdftotext -layout`

The PDF→text extraction inserted **3 form-feed characters** at PDF page
boundaries. They appear in non-message-body positions:

1. **Block 5 (Miguel Santana, Spanish clinic):**
   ```
   From: Miguel Santana\n\x0cEmail: m.santana@clinicavera.es\n...
   ```
   The `\x0c` is glued to the start of the `Email:` line, so a strict
   `^Email:` regex fails to match.

2. **Block 10 (Priya Ramanathan, multi-project):**
   ```
   Received: 2026-07-16 09:30\n\x0cMessage:\nTwo things we need...
   ```
   The `\x0c` is glued to the start of the `Message:` line.

3. **End of file:**
   ```
   ------------------------------------------------\n\x0c
   ```
   The final separator is followed by `\n\x0c`, creating a phantom 21st
   "empty block" containing only a form feed.

### 7b. Header-line-start assumption violated

Because of the form feeds, my header-count regex (`^Email:`) finds **19**
`Email:` headers, not 20. The Miguel Santana block has its `Email:` line
prefixed with `\x0c`, so it does not match `^Email:`.

### 7c. Trailing empty block

After the 20th enquiry's separator, the file ends with `\n\x0c`. A naive
split-on-separator approach would produce a 21st block containing only
`\x0c`, which would fail validation ("empty originalText") and crash the
import unless explicitly handled.

### 7d. Trailing blank line before each separator

Each enquiry's message body is followed by a blank line, then the separator:
```
...Do you do this kind of thing?
<blank line>
--------------------------------------------------------------------------------
```
The split captures the blank line as part of the block content. The parser
must decide whether to (A) include the trailing blank line in `originalText`
or (B) strip it.

---

## Proposed parser handling (non-destructive)

**Decision (will document in code + memory.md):**

1. **Form-feed (`\x0c`) handling:** Treat `\x0c` as **horizontal whitespace**
   for the purpose of identifying header-line starts only. The header regex
   will be `^[ \t\x0c]*(From|Email|Received|Message):[ \t]?(.*)$`. This
   consumes `\x0c` characters that appear **between headers** but NEVER
   touches the message body. If a form feed ever appears INSIDE a message
   body, it is preserved verbatim in `originalText`.

2. **Trailing empty block:** Detect blocks that contain only whitespace
   (including `\x0c`) and skip them with a `parserWarning` of
   `"empty block skipped"`.

3. **Trailing blank line in originalText:** Preserve EXACTLY what is in the
   file. `originalText` = bytes between the `Message:\n` header line and
   the next separator (or end of file). No stripping, no normalization.
   This honors Rules.md §14 ("Original enquiry text is immutable") and
   §13 ("Preserve the original uploaded content during parsing").

4. **Missing Email header (Miguel Santana block):** With the form-feed-aware
   regex, the `Email:` line WILL be matched. If a future block is missing
   the Email header entirely, the parser records `parserWarnings: ["missing
   Email header"]` and sets `sender.email = null`. The block still becomes
   a record.

5. **Preamble:** Text before the first separator is identified as the
   preamble and skipped (with a `parserMeta.preamble` field for
   informational purposes).

6. **From / Email / Received extraction:** Each is extracted from its
   header line. `receivedAt` is parsed as a Date from the `Received:`
   field (format `YYYY-MM-DD HH:MM`). If parsing fails,
   `receivedAt` falls back to `new Date()` (import time) and a warning
   is recorded.

**This handling is non-destructive to actual message content.** The only
"modification" is that form-feed characters BETWEEN headers are consumed
by the header regex (which is necessary to correctly identify the headers).
Form-feed characters inside message bodies would be preserved.

If the operator disagrees with this handling, they should veto before
Phase 3 begins. The parser is designed to make this behavior easy to
change (single regex constant).
